# AGENTS.md

Conventions for this repo — a static educational site (vanilla HTML/CSS/JS,
locally-vendored KaTeX) with three sections: Real Analysis, Optimization,
Statistics. Follow these when adding or editing content, especially SVG
diagrams.

## Site structure — separate pages, shared assets

Each section is its own real page, not a hash-toggled tab:

```
/real-analysis/index.html
/optimization/index.html
/statistics/index.html
```

`/index.html` at the root is just a redirect to `/real-analysis/`, for
anyone hitting the bare domain — it has no real content of its own.

`style.css`, `script.js`, and `vendor/katex/` live at the repo root and are
shared by all three pages via `../`-relative paths (each page is one
directory deep). When adding a new page, follow the same pattern: a
standalone HTML document with its own `<head>`/nav markup, referencing the
shared root assets with `../`, rather than duplicating CSS/JS per page.

The subject switcher (`<details class="menu-nav">` — a hamburger icon in
the top-left corner that opens a dropdown with the three subject links) is
duplicated at the top of each page's markup — there's no templating step,
so if its links, text, or styling change, update it in all three files.
The `active` class on the current page's own `.menu-item` is hardcoded per
file, not computed by JS. The open/close toggle itself is native
`<details>`/`<summary>` behavior, not JS — script.js only adds "close on
outside click" and "close on Escape" on top of it, so the menu still works
with JS disabled.

Content-wise, each page is just what used to be that tab's `<section
class="panel">` — same ids, same structure, same `.topic` divs — so
diagram/content conventions below apply identically regardless of which
page you're in.

Every `.topic` needs a unique `id` — besides being how same-page
cross-references work (e.g. the "complete" link in Open and Closed Sets),
script.js auto-injects a hover permalink icon ("#", GitHub-markdown style)
into any `.topic[id] h2` on page load. Don't hand-add an anchor tag to a
heading yourself; a new topic just needs the `id`, and it gets the icon
for free.

The same `.topic[id]` elements also drive the floating "on this page" TOC
in the right gutter (`script.js`, `.toc` in `style.css`) — built fresh per
page on load, so a new topic appears in it automatically too. It's hidden
below the 1280px viewport-width breakpoint, where there's no longer room
for a gutter beside the centered content column.

## Diagram font size and scaling — always 1:1

Every SVG on the site, whether hand-written in `index.html` or generated by
`script.js`, must render text at exactly its declared `font-size` — no
scaling drift.

**The rule:** every `<svg>` element must carry an inline style pinning its
rendered width to its own `viewBox` width:

```html
<svg viewBox="0 0 220 150" style="width:220px;max-width:220px;" ...>
```

or, when building a `<svg>` programmatically in `script.js`:

```js
const svg = el('svg', {
  viewBox: `0 0 ${width} ${height}`,
  style: `width:${width}px;max-width:${width}px`,
  ...
});
```

**Why:** a container CSS rule like `.viz svg { max-width: 280px; }` only
pins the *rendered* width if every diagram using that class happens to
share the same `viewBox` width. The moment one diagram's `viewBox` width
differs (e.g. an LP graph whose computed width depends on `xMax`/`yMax`),
the rendered-width-to-viewBox-width ratio stops being 1, every `font-size`
in that diagram scales up or down with it, and the real on-screen text size
silently stops matching what's declared in the markup. This happened
twice independently (once in Real Analysis, once in the Optimization LP
graphs and Dijkstra diagram) before the inline-style pin became the fix.
Pinning per-SVG, not per-CSS-class, makes the fix hold regardless of how
many different diagram sizes share a container class.

**Also:** use one `font-size` value for all diagram text, site-wide — `12`.
Don't vary size for visual hierarchy (emphasis, titles vs. tick labels);
use `font-weight` and `fill` color for that instead. This keeps every
label on the page the same real size no matter which diagram it's in.

**Verifying:** after touching any diagram, check with Playwright that for
every `<svg>` in play, `rect.width / viewBox.width === 1` and every `text`
element's `fontSize * scale` comes out to the same value. A quick snippet:

```js
const svgs = Array.from(document.querySelectorAll('svg'));
for (const svg of svgs) {
  const rect = svg.getBoundingClientRect();
  const vb = svg.viewBox.baseVal;
  const scale = rect.width / vb.width; // should always be 1
}
```

## Diagram color key

Colors are assigned by grammatical role, consistently across every topic —
not by which specific set/diagram they appear in:

- `#4078F2` blue — function names / metrics
- `#7B4B8C` purple — quantifiers / operators
- `#C18401` gold — named sets, drawn as the region/line that *is* the set
- `#1a1a1a` black — generic points (sequence terms, arbitrary points) —
  stays generic-colored regardless of whether that point happens to be a
  member of a named set, *unless* there's no other gold element in the
  diagram to identify the set (see Dense Sets, Completeness's ℚ card)
- `#999` / `#ccc` muted gray — ambient space / secondary reference lines

Gold fill on a continuous line or region asserts "this entire extent
equals the named set" — don't use it for sets that aren't actually
fillable intervals/regions (e.g. ℚ, which has gaps everywhere).

## Workflow

- Verify every content or diagram change with Playwright before
  committing: check for paragraph/math overflow (`scrollWidth >
  clientWidth`), SVG text clipping (`getBBox()` vs `viewBox`), and
  console/page errors.
- Commit after each logical change with a descriptive message explaining
  the "why," not just the "what."
