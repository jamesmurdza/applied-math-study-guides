# AGENTS.md

Conventions for this repo — a static educational site (vanilla HTML/CSS/JS,
locally-vendored KaTeX) with three sections: Real Analysis, Optimization,
Statistics. Follow these when adding or editing content, especially SVG
diagrams.

## Site structure — separate pages, shared assets

Each section is its own real page, not a hash-toggled tab:

```
/real-analysis/index.html
/optimization/index.html
/statistics/index.html
```

`/index.html` at the root is just a redirect to `/real-analysis/`, for
anyone hitting the bare domain — it has no real content of its own.

`style.css`, `script.js`, and `vendor/katex/` live at the repo root and are
shared by all three pages via `../`-relative paths (each page is one
directory deep). When adding a new page, follow the same pattern: a
standalone HTML document with its own `<head>`/nav markup, referencing the
shared root assets with `../`, rather than duplicating CSS/JS per page.

The subject switcher (`<details class="menu-nav">` — a hamburger icon in
the top-left corner that opens a dropdown with the three subject links) is
duplicated at the top of each page's markup — there's no templating step,
so if its links, text, or styling change, update it in all three files.
The `active` class on the current page's own `.menu-item` is hardcoded per
file, not computed by JS. The open/close toggle itself is native
`<details>`/`<summary>` behavior, not JS — script.js only adds "close on
outside click" and "close on Escape" on top of it, so the menu still works
with JS disabled.

Content-wise, each page is just what used to be that tab's `<section
class="panel">` — same ids, same structure, same `.topic` divs — so
diagram/content conventions below apply identically regardless of which
page you're in.

Every `.topic` needs a unique `id` — besides being how same-page
cross-references work (e.g. the "complete" link in Open and Closed Sets),
script.js auto-injects a hover permalink icon ("#", GitHub-markdown style)
into any `.topic[id] h2` on page load. Don't hand-add an anchor tag to a
heading yourself; a new topic just needs the `id`, and it gets the icon
for free.

The same `.topic[id]` elements also drive the floating "on this page" TOC
in the right gutter (`script.js`, `.toc` in `style.css`) — built fresh per
page on load, so a new topic appears in it automatically too. It's hidden
below the 1280px viewport-width breakpoint, where there's no longer room
for a gutter beside the centered content column.

On pages with enough topics to benefit from it (currently just
Statistics), topics are grouped under a plain `<h2 class="group-heading">`
("Parameter Estimation", "Hypothesis Testing", etc.) placed directly in
`.topics` as a sibling of the `.topic` divs — deliberately *not* nested
inside a `.topic[id]`. script.js's permalink-icon and TOC-building loops
both query `.topic[id]` / `.topic[id] h2` specifically, so a heading
outside that structure is automatically invisible to both: no anchor icon,
no TOC entry, zero script.js changes needed to support it. It shares the
`h2` tag with every topic's own heading (visually distinguished instead
via `.group-heading`'s CSS — small, uppercase, muted) rather than using a
semantically-more-correct higher-weight tag, since script.js's heading
queries are hardcoded to `h2` across all three pages and changing that
site-wide wasn't worth it for one page's grouping.

## Diagram font size and scaling — 1:1 at normal widths, responsive below that

Every SVG on the site, whether hand-written in a page's `index.html` or
generated by `script.js`, must render text at exactly its declared
`font-size` whenever the page is wide enough to show it at natural size —
no scaling drift between diagrams that are supposed to look the same size.
Below that, it should shrink responsively with the viewport rather than
overflow it.

**The rule:** every `<svg>` element must carry an inline style pinning its
*max* rendered width to its own `viewBox` width, while staying fluid
(`width:100%`) below that:

```html
<svg viewBox="0 0 220 150" style="width:100%;max-width:220px;" ...>
```

or, when building a `<svg>` programmatically in `script.js`:

```js
const svg = el('svg', {
  viewBox: `0 0 ${width} ${height}`,
  style: `width:100%;max-width:${width}px`,
  ...
});
```

**Why `max-width` per-SVG, not a shared CSS class:** a container rule like
`.viz svg { max-width: 280px; }` only pins the rendered width consistently
if every diagram using that class happens to share the same `viewBox`
width. The moment one diagram's `viewBox` width differs (e.g. an LP graph
whose computed width depends on `xMax`/`yMax`), the rendered-width-to-
viewBox-width ratio stops being 1, every `font-size` in that diagram
scales up or down with it, and the real on-screen text size silently
stops matching what's declared in the markup. This happened twice
independently (once in Real Analysis, once in the Optimization LP graphs
and Dijkstra diagram) before pinning each SVG's own max-width to its own
viewBox width became the fix.

**Why `width:100%`, not a fixed `width:Npx`:** a fixed pixel width doesn't
shrink on narrow viewports, so on a phone-width screen an SVG wider than
the available content column overflows it — and because `body` centers
`.container` via flex, that overflow shows up as a lopsided page (space on
one side, none on the other, not a symmetric scrollbar) rather than an
obviously-broken layout. This happened site-wide before `width:100%`
(fluid, capped by `max-width`) replaced a hardcoded `width:Npx` as the
standard. Scale will legitimately be below 1 on narrow viewports now —
that's correct, not drift; drift is inconsistency *between* diagrams at
the same width, not intentional shrinking as the width changes.

**Related trap — CSS Grid and `min-width: auto`:** a grid item (like
`.set-card`) defaults to `min-width: auto`, which refuses to shrink below
its content's natural size regardless of the grid track's own sizing —
so a `width:100%` SVG inside it still overflowed a narrow viewport even
after the fix above, because the *card* wouldn't shrink to let it. Fixed
with `min-width: 0` on `.set-card`. Keep this in mind for any new
grid-based layout: a fluid child doesn't help if its grid-item parent
won't shrink.

**Also:** use one `font-size` value for all diagram text, site-wide — `12`.
Don't vary size for visual hierarchy (emphasis, titles vs. tick labels);
use `font-weight` and `fill` color for that instead. This keeps every
label on the page the same real size no matter which diagram it's in.

**Verifying:** after touching any diagram, check with Playwright that
`document.documentElement.scrollWidth` never exceeds `window.innerWidth`
at narrow widths (375px is a good smoke test), and that at normal content
widths (900px+) every `<svg>`'s `rect.width / viewBox.width === 1` with
every `text` element's `fontSize * scale` coming out to the same value.
Quick snippets:

```js
// narrow-viewport overflow check
document.documentElement.scrollWidth > window.innerWidth // should be false

// normal-width scale check
const svgs = Array.from(document.querySelectorAll('svg'));
for (const svg of svgs) {
  const rect = svg.getBoundingClientRect();
  const vb = svg.viewBox.baseVal;
  const scale = rect.width / vb.width; // should be 1 at 900px+ viewport width
}
```

## No inline math — `$$...$$` display blocks only

`script.js`'s `renderMathInElement` call only registers one delimiter,
`{ left: '$$', right: '$$', display: true }` — there's no inline `$...$`
delimiter configured. A single-dollar expression dropped into a `<p>` for
a quick inline symbol (e.g. "the total is `$I_n(\theta) = n I_1(\theta)$`")
silently renders as literal, un-rendered LaTeX source text instead of
math — KaTeX never touches it, and there's no error to catch it. This
happened once (Statistics' Fisher Information topic). For a symbol or
short expression inside running prose, use the same plain-Unicode style
already used throughout (`θ̂`, `μ₀`, `I₁(θ)`, `n·I₁(θ)`) rather than LaTeX
delimiters; save `$$...$$` for standalone `p.math` display equations.

## Copying a rendered equation copies its LaTeX source

Selecting rendered KaTeX output and copying it would otherwise paste as
garbled text — KaTeX builds formulas from many individually-positioned
spans for visual layout, and that DOM order isn't reading order. Fixed
site-wide by vendoring KaTeX's own official extension for exactly this,
`vendor/katex/copy-tex.min.js` (fetched from the same `0.16.11` release as
the rest of `vendor/katex/`, matching the "locally-vendored" convention —
no CDN reference), included via `<script>` on all three pages right after
`auto-render.min.js`. It needs no init call and no CSS: it just installs a
global `copy` listener that, when the selection touches a `.katex`
element, expands the selection to the whole formula and rewrites the
clipboard's plain-text data to the original TeX pulled from KaTeX's own
`<annotation encoding="application/x-tex">` (already present in every
formula's hidden MathML output, since nothing on this site overrides
KaTeX's default `output: "htmlAndMathml"`) — wrapped in `$...$` for inline
math or `$$...$$` for `.katex-display` blocks. A selection spanning both
prose and a formula keeps the prose as plain text and only rewrites the
formula part. Verify with Playwright by selecting a `.katex` element's
contents, dispatching a copy, and reading `navigator.clipboard.readText()`
back — it should equal the formula's own delimited TeX source, not the
rendered glyphs' text content.

## Equations shrink too, the same way diagrams do

A `$$...$$` display equation has no `viewBox` to pin a `max-width` to, but
it follows the identical rule: full declared size whenever it fits, fluid
shrinking below that, never a scrollbar. `script.js` enforces this after
every KaTeX render (`fitMathBlocks()`, also re-run on `resize` and once
`document.fonts.ready` resolves, since KaTeX's own math fonts load async
and swap in after the first measurement) — new `.topic > p.math` blocks
get this for free and need no manual handling.

**Why this needed real measurement, not just CSS:** `.katex-display` is
`display:block` (from katex.css), so its own `offsetWidth`/`scrollWidth`
are clamped to the paragraph's width — they can't reveal that KaTeX's
inner `.base` span (the actual glyphs, `display:inline-block`) already
needs more room and is silently overflowing past it. The fix measures the
true natural width by toggling `.katex-display` to `display:inline-block`
just long enough to read its shrink-to-fit `offsetWidth`, then reverts it.

**Why the scale has to originate from the left edge, not center:** an
overflowing formula renders flush with the paragraph's left edge, not
centered — confirmed by comparing an inner span's position before and
after scaling. `transform-origin: left top` shrinks from that same edge,
so the result still sits flush left with zero overflow; `center top`
scales by the right *amount* but around the wrong point, leaving the same
overflow on the right that the shrink was supposed to remove.

**Why `.topic .math` is `overflow: hidden` on *both* axes, not just
`overflow-x`:** the shrink above is meant to make scrolling unnecessary,
not just unnecessary *most* of the time — a non-`visible` `overflow-x`
with no `overflow-y` makes the box a scroll container even when nothing
truly overflows, which trackpads/wheels render as a tiny rubber-band
nudge on any scroll gesture over it (reported directly, twice: "if i put
my cursor over an equation and scroll, it scrolls a tiny bit," then "but
it's a y problem not x" once the first pass only set `overflow-x`). That
second report was the real bug: per spec, an element can't mix `visible`
on one axis with non-`visible` on the other — leaving `overflow-y`
unset while `overflow-x` is `hidden` silently computes it to `auto`, not
`visible`. And KaTeX's own internal baseline "struts" (invisible spacers
it uses to stack sub/superscripts and fractions at the right height)
render a few px taller than the box in *every* formula regardless of
width or scale — so that implicit `overflow-y: auto` was a guaranteed
scrollbar on every single equation, not an edge case. Setting the
shorthand `overflow: hidden` (both axes explicitly) fixed it; the
vertical "overflow" it now clips is just those invisible struts, not
visible glyph content — confirmed by screenshotting tall formulas (nested
fractions, `\sum`/`\prod`, `\left[...\right]` brackets) and checking
nothing is actually cut off.

That raises the stakes on the horizontal fit being exact, since any
shortfall now silently clips a glyph instead of just being scrollable —
so the scale computation subtracts a 3px safety margin from the available
width, covering compounding sub-pixel rounding (`offsetWidth` itself
rounds to the nearest integer, and the transform matrix's own
pixel-snapping can round up on top of that). 1px wasn't enough margin in
practice; a clipped `μ₀` subscript on the narrowest formula is what
caught it.

**Verifying:** after touching equation-heavy content, additionally check
that no `.topic .math` has `scrollWidth > clientWidth` at narrow widths,
that every `.topic .math` computes to `overflow-x`/`overflow-y: hidden`
(not `auto` on either axis — that's the actual scroll-container test, not
`scrollHeight > clientHeight`, which is harmlessly nonzero on *every*
formula because of KaTeX's own struts), and that `.katex-display`
elements carry no transform at 900px+ (nothing should ever shrink when it
doesn't need to):

```js
Array.from(document.querySelectorAll('.topic .math')).filter(el =>
  el.scrollWidth > el.clientWidth + 1 ||            // real horizontal overflow
  getComputedStyle(el).overflowY !== 'hidden'        // a scroll container exists
) // should be empty
```

## Diagram color key

Colors are assigned by grammatical role, consistently across every topic —
not by which specific set/diagram they appear in:

- `#4078F2` blue — function names / metrics
- `#7B4B8C` purple — quantifiers / operators
- `#C18401` gold — named sets, drawn as the region/line that *is* the set
- `#1a1a1a` black — generic points (sequence terms, arbitrary points) —
  stays generic-colored regardless of whether that point happens to be a
  member of a named set, *unless* there's no other gold element in the
  diagram to identify the set (see Dense Sets, Completeness's ℚ card)
- `#999` / `#ccc` muted gray — ambient space / secondary reference lines

Gold fill on a continuous line or region asserts "this entire extent
equals the named set" — don't use it for sets that aren't actually
fillable intervals/regions (e.g. ℚ, which has gaps everywhere).

## Workflow

- Verify every content or diagram change with Playwright before
  committing: check for paragraph/math overflow (`scrollWidth >
  clientWidth`), SVG text clipping (`getBBox()` vs `viewBox`), and
  console/page errors.
- Commit after each logical change with a descriptive message explaining
  the "why," not just the "what."
